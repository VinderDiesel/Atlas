# ADR-0001：为什么使用 TPC-DS 公开数据而非真实企业数据

- 日期：<填写起始日期>
- 状态：accepted
- 相关：README 第 7 节（数据来源与诚实边界）

## 背景

本项目是个人在业余时间建设的设计验证项目，需要一套具备真实复杂度的零售数据来承载
语义层、指标平台与 NL2SQL 的端到端验证。但存在以下硬约束：

1. 无法获取真实企业数据（无授权来源）
2. **严禁**使用前雇主/现雇主的任何数据、代码、指标定义（合规红线）
3. 个人预算有限，无法承担 PB 级存储与计算

## 备选方案

| 方案 | 优势 | 劣势 |
|---|---|---|
| 真实企业数据 | 复杂度真实，最能说明问题 | 无来源；有合规风险；不可对外公开 |
| 自造假数据 | 完全可控 | 太简单，无法体现 schema linking 等真实难点 |
| **TPC-DS SF1** | 公开可复现；24 张表；真实零售 ER 复杂度；社区认可 | 与真实企业 PB 级、上千表规模不可比 |
| Spider / BIRD | 学术标准，便于对照 | 单库规模小，不适合做指标平台载体 |

## 决策

以 **TPC-DS SF1（约 1GB）** 作为主数据底座重建零售场景，
以 **Spider / BIRD** 作为公开集能力对照，以**自建 50 条黄金集**作为主评测集。

## 理由

1. **可复现优先于真实感**：任何 reviewer 都能自己生成同样的数据，评测结果可验证
2. **可公开优先于复杂度**：GitHub 仓库要能公开，才能作为能力证明
3. TPC-DS 的星型/雪花模型、缓慢变化维、多粒度事实表足以承载指标平台的真实问题

## 代价与限制

- 规模差距：1GB vs 真实 PB 级，压缩、分区、物化策略无法真实验证
- Schema 规模：24 张表 vs 真实上千张表，**大规模 schema linking 属于未验证假设**
- 数据质量：TPC-DS 数据干净，真实场景的脏数据、迟到数据、口径漂移无法体现
- 业务语义：TPC-DS 是合成数据，指标定义由本人人工构造，不代表真实业务口径

## 验证方式

- 能在固定快照 sha 上稳定复现所有评测结果 → 可复现性成立
- 若未来接入真实数据，需重新验证：schema linking 规模效应、权限模型、物化策略
