# ADR-0003：只读 SQL 网关设计

- 日期：<填写>
- 状态：accepted
- 相关：AGENTS.md 第 1 节 N3、README 第 6 节

## 背景

NL2SQL 最大的落地阻力不是准确率，而是**企业不敢把生成的 SQL 直接打到生产库**。
Atlas 需要一个不可绕过的安全边界。

## 备选方案

| 方案 | 优势 | 劣势 |
|---|---|---|
| 仅用数据库只读账号 | 简单 | 无法限制扫描量；无法注入行级权限；无法审计到问句粒度 |
| 正则匹配黑名单 | 实现快 | 极易绕过（注释、嵌套、编码变形） |
| **AST 白名单 + 策略注入 + 成本估算** | 结构化、不可绕过、可审计 | 实现复杂，需覆盖方言边界 |
| 只允许预编译查询（禁用自由 SQL） | 最安全 | 丧失自由探索能力，产品价值大减 |

## 决策

采用 **AST 解析 + 白名单校验 + 策略注入 + 成本估算** 的强制执行链，
并配合**数据库只读账号**做纵深防御（不依赖单一层）。

## 强制执行链（顺序不可调换）

```
parse(AST)
  → 禁 DDL/DML（Insert/Update/Delete/Drop/AlterTable/Grant/Copy）
  → 函数黑名单
  → apply LIMIT（MAX_QUERY_ROWS）
  → apply 时间范围（MAX_QUERY_DAYS）
  → 注入行级策略谓词（RowPolicy → SQL 谓词）
  → 成本估算（扫描行数 / 预估费用）
  → 超预算则拒绝
  → 执行
```

## 理由

1. AST 层面无法用注释或编码绕过
2. 权限下推到 SQL 谓词层，而非应用层过滤——应用层过滤意味着数据已出库
3. 成本估算防止一条烂 SQL 打爆集群

## 代价与限制

- 必须覆盖的边界：CTE、子查询、视图展开、动态 SQL、函数黑名单、权限表达式注入
- 视图展开可能绕过表级白名单，需要递归解析
- 成本估算依赖统计信息，冷启动不准

## 验证方式

构造 10 条恶意/危险 SQL（含 CTE 嵌套、视图绕过、无 LIMIT 大扫描），
**全部必须被拦截**，且这 10 条固化为测试用例（pytest marker: `security`）。
